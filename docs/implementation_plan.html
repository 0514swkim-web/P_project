A. 웹캠·촬영 환경 확인

11주차 · 약 30분
왜 하나모든 데이터가 이 웹캠으로 찍힙니다. 처음에 설정·위치를 정해 두지 않으면 나중에 찍은 데이터와 조건이 달라져 비교가 안 됩니다.
  1. ZIO-C960 연결 후 얼굴 추적 끄기 — 화면이 사람을 따라 움직이면 좌표가 틀어집니다. 전용 앱/설정이 있으면 끄고, 없으면 몸을 움직여 화면이 따라오는지 확인합니다.
  2. 환경 확인 스크립트 실행 
    .venv 터미널에서
python scripts\check_env.py --camera 1                      # 기본 1280×720
python scripts\check_env.py --camera 1 --width 1920 --height 1080   # 비교용
    화면 위쪽의 FPS와 infer ms(손 인식 시간)를 봅니다. 두 해상도 중 FPS가 30에 가깝고 손 인식이 안정적인 쪽을 고릅니다. 보통 1280×720 권장: MediaPipe가 어차피 내부에서 작게 줄여 처리하므로 해상도를 올려도 이득이 적습니다.
  3. 깜빡임 확인 — 형광등·LED 아래에서 가로 줄무늬나 밝기 깜빡임이 보이는지 봅니다. 보이면 자연광이 있는 자리로 옮기거나 조명을 바꿉니다.
  4. 촬영 위치 고정·기록 — 사용자 정면, 손은 카메라에서 50cm 이상, 배경은 단순하게. 웹캠 위치를 사진으로 찍어 두고 높이·거리를 메모합니다(재현용).
완료 기준FPS가 27~30을 유지하고, 손을 천천히 움직여도 21개 점이 끊기지 않음. 해상도·위치·조명이 메모로 남아 있음.
막히면 · 화면이 안 뜨거나 내장 카메라가 뜸 → --camera 0, --camera 2로 바꿔 보기
· FPS가 15 근처 → 조명을 밝게(어두우면 웹캠이 스스로 FPS를 낮춤), --no-mjpg와 비교해 MJPG가 적용됐는지 확인

C. 파일럿 수집 + 규칙 임계값 튜닝

11주차 · 2~3시간
왜 하나규칙 판별기(rules.py)의 임계값은 가짜 손 기준으로 정한 값입니다. 진짜 손은 엄지 각도가 덜 펴져 보이는 등 차이가 있어서, 내 손으로 먼저 맞춰 본 뒤 팀원 데이터를 받아야 수집을 두 번 하지 않습니다.

개념: 규칙 판별기는 어떻게 판단하나

손가락마다 관절 각도를 잽니다. 쭉 편 손가락은 관절이 거의 일직선(180°)이고, 접으면 각도가 작아집니다. 각도가 임계값보다 크면 "펴짐(1)", 작으면 "접힘(0)"으로 보고, 5개 손가락 패턴(예: 샤카 = 10001)으로 제스처를 정합니다.

RuleConfig 값현재뜻
finger_extended_deg150°검지~소지: 두 관절 각도 평균이 이보다 크면 펴짐
thumb_extended_deg140°엄지 관절 각도 기준 (엄지는 굽는 방향이 달라 따로 둠)
thumb_away_dist0.6엄지 끝이 검지 뿌리에서 이만큼 떨어져야 펴짐 (손바닥 크기 = 1)
ok_touch_dist0.25엄지 끝과 검지 끝이 이보다 가까우면 OK의 "맞닿음"

할 일

  1. 내 손으로 파일럿 수집 — 수집 화면 둘째 줄에 규칙 판별 결과와 손가락 패턴(예: rule: call (0.82) 10001)이 실시간으로 나옵니다. 녹화하면서 동시에 규칙이 맞는지 눈으로 확인할 수 있습니다. 
    python scripts\collect_landmarks.py --participant P01 --session pilot --condition bright_front --camera 1
# 1~9 키: 라벨 선택 (palm,fist,peace,call,rock,ok,like,one,none)
# SPACE: 녹화 시작/정지 (한 번 = trial 1개)   q: 종료
    라벨마다 3회 × 3초 정도, 손을 조금씩 기울이거나 거리를 바꿔 가며 찍습니다.
  2. 틀리는 경우 메모 — 예: "샤카인데 00001로 나옴 → 엄지가 접힘으로 판정됨".
  3. 각도 분포 확인 같이 만들 것 — 파일럿 CSV에서 라벨별·손가락별 각도를 히스토그램으로 그리는 노트북(notebooks/rule_tuning.ipynb)을 만듭니다. "펴진 엄지"와 "접힌 엄지" 각도 분포가 겹치지 않는 사이에 임계값을 두는 것이 원리입니다.
  4. 임계값 수정 → 테스트 — src/gesture/rules.py의 RuleConfig 기본값을 바꾸고 python -m pytest -q. 테스트가 깨지면 가짜 손 기준 테스트라서 그런지 확인한 뒤 함께 조정합니다.
완료 기준8개 모양(palm, fist, peace, call, rock, ok, like, one)을 정면과 약간 기울인 상태에서 해 봤을 때 규칙 판별이 대부분 맞음. 특히 call·like의 엄지. 바꾼 값과 이유를 gesture_candidates.md에 기록.
막히면엄지가 끝까지 불안정하면 각도 대신 거리 기준(thumb_away_dist) 비중을 높이거나, 클러치 1순위를 락🤘으로 바꾸는 근거로 씁니다. 이것도 중요한 결과이니 기록해 두세요. 규칙이 완벽할 필요는 없습니다. F단계의 학습 분류기가 보완합니다.

※ 파일럿 데이터(--session pilot)는 튜닝에 쓴 데이터라 최종 평가에서는 빼야 합니다.

D. 팀원 데이터 수집

11~12주차 · 1인당 약 30분
왜 하나분류기 학습(F), 클러치 비교(E), 평가(I) 모두 이 데이터로 합니다. 사람마다 손 크기·습관이 달라서 여러 사람의 데이터가 꼭 필요합니다. 영상은 저장하지 않고 손 좌표만 CSV로 남깁니다(개인정보·용량).

개념: 참여자·조건·trial

  • 참여자(participant): P01(나), P02~P04(팀원), P05~(외부). 학습·평가를 사람 단위로 나누는 기준입니다. 같은 사람이 학습과 평가 양쪽에 있으면 점수가 부풀려집니다.
  • 조건(condition): 조명·각도 등 촬영 상황. 예) bright_front, dim_front, bright_side. 조건별 정확도를 따로 보고 약점을 찾습니다.
  • trial: SPACE로 녹화를 시작해서 멈출 때까지의 한 구간. 오작동률·활성화 실패율은 trial 단위로 셉니다.

수집 세트 1 · 제스처 (분류기 학습·정확도용)

python scripts\collect_landmarks.py --participant P02 --condition bright_front --camera 1
python scripts\collect_landmarks.py --participant P02 --condition dim_front    --camera 1  # 선택
python scripts\collect_landmarks.py --participant P02 --condition bright_side  --camera 1  # 선택

palm, fist, peace, call, rock, ok, like, one모양을 유지한 채 손을 천천히 움직이고 살짝 기울이기라벨당 5 trial × 3초 (≈ 450프레임)
none명령이 아닌 손 모양: 반쯤 쥔 손, 손가락 3개, 손 옆면, 편하게 늘어뜨린 손 등5 trial × 3초, 매번 다른 모양

  --labels nonop_drink,nonop_head,nonop_wave,nonop_phone,nonop_point,activate_call,activate_rock,activate_ok
라벨찍는 방법분량 (1인)

  • 수집 로그 작성: 날짜, 장소, 조명, 웹캠 위치, 참여자 ID, 특이사항 (보고서의 "실험 조건"이 됩니다)

E. 클러치 후보 비교·확정

12주차 · 1~2시간
왜 하나클러치는 로봇을 켜고 끄는 스위치라서 평소 손짓에 잘못 켜지지 않는 것(오작동률)과 하려고 할 때 잘 켜지는 것(활성화 실패율)이 둘 다 중요합니다. 계획서대로 데이터로 비교해 확정합니다.

할 일

  1. 후보 3개를 같은 데이터로 평가합니다 (C에서 맞춘 규칙 기반). 
    python scripts\evaluate.py --data "data\raw\*.csv" --clutch call --out results\clutch_call.json
python scripts\evaluate.py --data "data\raw\*.csv" --clutch rock --out results\clutch_rock.json
python scripts\evaluate.py --data "data\raw\*.csv" --clutch ok   --out results\clutch_ok.json
  2. 결과를 아래 표로 정리합니다. 수치 뒤 괄호는 95% 신뢰구간입니다(참여자 단위).
    후보오작동률 (≤5%)가장 잘 오인되는 동작활성화 실패율 (≤10%)활성화까지 평균 시간사용 편의 (설문)
    call 🤙
    rock 🤘
    ok 👌
  3. 결정 규칙: ① 오작동률 5% 이하를 만족하는 후보 중 → ② 활성화 실패율이 낮은 것 → ③ 비슷하면 팀원이 하기 편하다고 한 것.
  4. 확정한 후보를 src/gesture/state_machine.py의 default_roles()에 반영하고 테스트를 실행합니다. gesture_candidates.md를 v1.0(확정)으로 고쳐 팀에 공유합니다.
완료 기준비교표와 결정 이유가 문서에 남고, 코드 기본값이 확정 후보로 바뀜.
주의여기서 쓴 참여자의 비조작 데이터는 클러치를 "고르는 데" 쓴 것이므로 최종 오작동률 평가에서는 제외합니다(계획서 설계 결정 6). 결과가 모두 목표에 못 미치면 clutch_hold_s(0.5초)·stable_frames(3) 조정도 함께 검토합니다.

F. 분류기 학습·선정

12주차 · 1~2시간
왜 하나규칙은 사람이 정한 기준이라 애매한 손에 약합니다. 학습 분류기는 데이터에서 직접 경계를 배웁니다. 규칙 · 랜덤 포레스트 · MLP 세 가지를 같은 조건으로 비교해 정확도와 속도 기준으로 하나를 고릅니다.

개념

  • 특징 78차원: 손목을 원점으로, 손바닥 크기를 1로 맞춘 21점 좌표 + 손가락 관절 각도. 왼손은 좌우를 뒤집어 오른손처럼 만듭니다.
  • GroupKFold(참여자 단위 교차검증): 4명이면 "3명으로 학습 → 남은 1명으로 시험"을 4번 돌려 평균. 처음 보는 사람에게도 통하는지를 봅니다.
  • macro-F1: 클래스별 F1의 평균. 데이터가 적은 클래스도 똑같이 반영되어 정확도보다 공정합니다.

할 일

python scripts\train_classifier.py --data "data\raw\*.csv"
# 결과: results\train_report.json, results\confusion_*.png, models\gesture_clf.joblib
  1. train_report.json에서 방법별 정확도·macro-F1·판별 시간을 비교합니다.
  2. confusion_*.png(혼동행렬)에서 어떤 쌍이 헷갈리는지 봅니다. 예상되는 쌍: like↔fist, rock↔one, peace↔one.
  3. 선정 기준: 판별 5ms 미만인 것 중 macro-F1이 가장 높은 것. 지금까지 측정으로는 랜덤 포레스트가 7.5ms라 그대로는 탈락이고, MLP(0.22ms)가 유력합니다. 랜덤 포레스트가 정확도에서 크게 앞서면 트리 수를 줄여 다시 재 봅니다.
  4. 선정 모델로 평가: python scripts\evaluate.py --model models\gesture_clf.joblib --clutch (확정 후보)
완료 기준방법 비교표, 혼동행렬, 선정 이유가 정리됨. 참여자 교차검증 macro-F1이 규칙 기반보다 높고 판별이 5ms 미만.

G. 실시간 데모 통합 새로 만들 것

12주차 · 같이 구현 2~3시간
왜 하나지금까지는 녹화된 CSV로만 평가했습니다. 실제 사용은 실시간이므로 웹캠 → 판별 → 상태 머신을 한 번에 돌려 클러치·그리퍼가 체감상 자연스러운지 확인해야 합니다. ROS 없이 Windows에서 돌아가므로 팀 시연·멘토링 자료로도 바로 쓸 수 있습니다.

만들 것: scripts/live_demo.py

  • 웹캠(open_camera) → 손 인식(HandDetector) → GestureRecognizer(규칙 또는 학습 모델) → HandState
  • 화면 표시: 제어 모드(IDLE/PLANAR/HEIGHT/PAUSED), 그리퍼, 높이 입력, 클러치 진행 막대(0.5초), FPS, 판별 ms
  • 옵션: --model, --clutch, --camera, --log(HandState를 CSV로 저장)
python scripts\live_demo.py --camera 1 --model models\gesture_clf.joblib --clutch call --log results\live_log.csv
덤: 팀원B와 미리 맞춰 보기--log로 남긴 HandState 기록을 팀원B에게 주면, ROS 연동 전에도 "이런 값이 이런 순서로 온다"를 보고 명령 생성 로직을 테스트할 수 있습니다.
완료 기준30 FPS 유지, 판별 5ms 미만. 클러치로 켜고 끄기, 손바닥/주먹 그리퍼, V자 높이 모드가 화면에서 의도대로 바뀜. 손을 화면 밖으로 빼면 PAUSED.

H. Ubuntu + ROS 2 노드 연동 새로 만들 것

12~13주차
왜 하나팀 시스템은 ROS 2로 연결됩니다. 내 모듈의 결과를 /hand/state 토픽으로 내보내야 팀원B 노드가 받아서 Gazebo/로봇을 움직일 수 있습니다.

사전 준비

  1. Ubuntu 24.04 듀얼부팅 (docs/dev_environment.md B절: BitLocker 복구 키, 100GB, 백업 먼저)
  2. ROS 2 Jazzy Desktop + ros-jazzy-ros-gz 설치
  3. 가장 먼저: Ubuntu 기본 Python 3.12에서 pip install mediapipe==1.2.2가 되는지 확인
  4. 가상환경은 ROS 패키지가 보이도록: python3 -m venv --system-site-packages .venv

구현 순서

  1. 메시지 패키지 hand_interfaces — msg/HandState.msg를 hand_state_format 합의안대로 작성. 누가 만들지는 B에서 정한 대로.
  2. 노드 gesture_node (rclpy) — 지금의 GestureRecognizer를 그대로 불러 쓰고, 결과만 ROS 메시지로 바꿔 발행합니다. 로직을 다시 짜지 않는 것이 핵심입니다. 
    class GestureNode(Node):
    def __init__(self):
        super().__init__("gesture_node")
        qos = QoSProfile(depth=1, reliability=ReliabilityPolicy.BEST_EFFORT)
        self.pub = self.create_publisher(HandState, "/hand/state", qos)
        self.rec = GestureRecognizer(aspect, classifier=clf)      # 지금 코드 재사용
    def on_frame(self, landmarks, handedness, score, stamp):
        s = self.rec.process(stamp, landmarks, handedness, score) # → 파이썬 HandState
        self.pub.publish(to_msg(s, stamp))                        # → ROS 메시지
    입력은 B의 Q5 결정에 따라 ① 팀원A 함수를 같은 노드에서 호출하거나 ② /hand/landmarks 토픽을 구독합니다.
  3. 단독 확인: ros2 topic echo /hand/state(값이 맞는지), ros2 topic hz /hand/state(약 30 Hz)
  4. 연동 확인: 팀원B 노드 + Gazebo를 같이 띄워 클러치 → 손 이동 → 로봇 이동이 이어지는지 확인합니다.
  5. 지연 측정: 메시지의 header.stamp(카메라 캡처 시각)와 수신 시각의 차이를 기록합니다.
완료 기준Gazebo에서 손동작으로 로봇팔을 켜고·움직이고·집을 수 있음. /hand/state 30 Hz, 지연 수치 기록.

활성화 실패율의도적 클러치 trial 중 3초 안에 활성화 안 된 비율 (낮을수록 좋음)
